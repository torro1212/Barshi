# BARSHI — MASTER PRODUCT PROMPT

You are designing and defining **Barshi**, a next-generation AI-native creation platform for ages 11–15.

This document is the **full source of truth** for the product: vision, UX, behavior, safety model, learning philosophy, social system, moderation system, technical direction, and architecture.

Treat every section as binding product intent.

**Harmful:**

# 55. PLATFORM AND TECH DIRECTION

Barshi is a **web-first product** with a mobile-first responsive design.

No native app in MVP. The web app must feel as native as possible.

**Platform target:**
- Primary: Web (Chrome, Safari)
- Responsive: designed mobile-first, functional on desktop
- PWA-ready post-MVP (installable, offline draft support)

**Frontend:**
- Next.js 15 (App Router) with TypeScript
- Tailwind CSS v4 for styling
- Framer Motion for animations
- Zustand for state management

**Backend:**
- Next.js API routes (streaming)
- Supabase (PostgreSQL + Auth + Storage + Realtime)
- Upstash Redis for rate limiting

**AI / Generation:**
- Claude (Anthropic) as the primary generation model
- Model assignment: Sonnet for generation, Haiku for edits and safety scans
- All system prompts use prompt caching (cache_control: ephemeral)

**Project Format — Critical architectural decision:**
- Claude generates a **complete, self-contained HTML/CSS/JS file** directly
- This file is sanitized, stored in Supabase Storage, and served from `play.barshi.app`
- A lightweight JSON metadata object (screens, components, theme) is stored separately
- The metadata powers the System Map UI and AI edit context — it does NOT run in the browser
- The HTML file is what runs in the browser
- This is simpler, more powerful, and avoids building a custom renderer

**Game Engine:**
- All game-type projects use **Kaboom.js**, hosted on `cdn.barshi.app`
- Claude writes Kaboom.js code directly in the generated HTML
- Non-game types (websites, tools, stories) use vanilla HTML/CSS/JS only

**Thumbnails:**
- MVP: CSS-generated cover cards (gradient + icon + title, no screenshots needed)
- Post-MVP: Real screenshots via Browserless.io API

**Analytics:**
- PostHog for product funnel tracking

**Storage:**
- Supabase Storage for HTML bundles, thumbnails
- Each public project served from `play.barshi.app/{project-id}/index.html`

**Deployment:**
- Vercel for frontend + API routes
- Supabase managed for DB and storage
- Cloudflare or Vercel Edge for `play.barshi.app` sandbox CDN

# 57. AI GENERATION ARCHITECTURE

The generation pipeline:

1. **Intent collection** — user fills in the intent form
2. **Build plan generation** — Claude Haiku generates a structured build plan as JSON (fast, cheap)
3. **User reviews and edits plan** — shown in simple UI, user can modify
4. **Full generation** — Claude Sonnet generates a complete self-contained HTML/CSS/JS file
5. **Sanitization** — HTML is scanned for unsafe patterns and blocked APIs
6. **Storage** — clean HTML stored in Supabase Storage at `projects/{id}/index.html`
7. **Live preview** — the HTML file loads immediately in the builder sandboxed iframe

On each subsequent edit (Add / Change / Make Smarter / Fix):
1. User describes change in plain language
2. Claude Haiku receives: current HTML (truncated) + change request + meta_json
3. Claude returns complete updated HTML
4. System sanitizes → uploads to storage → iframe reloads

If generation fails at any point, the system falls back to a parameterized template for that project type. The user sees a starting version and can improve it.

Generation uses streaming responses wherever possible to show progress in real time.

Model usage per action:
- Build plan: claude-haiku-4-5 (fast, cheap JSON output)
- Full generation: claude-sonnet-4-6 (best quality for the most important moment)
- All edits (Add/Change/Fix/Smarter): claude-haiku-4-5 (fast iteration)
- Safety scan: claude-haiku-4-5 (high volume, must be instant)

All system prompts use Anthropic prompt caching (cache_control: ephemeral) to minimize cost on repeated calls.

---

# 58. SANDBOX SECURITY

All project previews and public project pages run in sandboxed iframes.

Sandbox restrictions:
- no access to parent window
- no localStorage / sessionStorage access outside sandbox
- no external network calls (CSP: default-src 'self')
- no ability to access device APIs
- generated code is sanitized before execution

Projects are served from a separate subdomain (e.g., `play.barshi.app`) to enforce origin isolation.

# 59. MONETIZATION DIRECTION

Barshi is free to use for all users.

Monetization model (post-MVP):
- **Barshi Pro (individual):** unlimited projects, custom domains for published projects, exclusive visual themes, priority generation
- **Barshi School (institutional):** class management, teacher dashboard, assignment flows, student analytics, COPPA/GDPR compliant

MVP launches free with no paywall. Growth and usage data will inform monetization timing.

Do not build monetization into the MVP. Design the product so it can be added without restructuring core flows.
